# 2. Gambaran Umum Arsitektur

Village Website CMS menggunakan arsitektur aplikasi monolitik modular berbasis Laravel.

Pendekatan ini dipilih karena:

1. Lebih sederhana untuk dikembangkan oleh tim kecil.
2. Mudah dijalankan pada shared hosting atau VPS ringan.
3. Tidak memerlukan pemisahan frontend dan backend.
4. Mudah dipelihara setelah masa KKN.
5. Mendukung penggunaan kembali pada instalasi desa lain.
6. Cocok dengan Blade, Filament, Eloquent ORM, queue, dan scheduler Laravel.

---

## 2.1 Model Arsitektur

```text
Guest / Admin
      ↓
Cloudflare
      ↓
Web Server
      ↓
Laravel Application
      ├── Public Frontend
      ├── Admin Dashboard
      ├── Business Services
      ├── Queue Workers
      └── Scheduler
      ↓
PostgreSQL Database
      ↓
File Storage
```

---

## 2.2 Jenis Aplikasi

Sistem merupakan:

```text
Modular Monolith
```

Seluruh modul berada dalam satu aplikasi dan satu deployment, tetapi dipisahkan berdasarkan tanggung jawab agar mudah dikembangkan dan dipelihara.

Sistem tidak menggunakan:

* Microservices.
* Frontend SPA terpisah.
* Database terpisah untuk setiap modul.
* API gateway.
* Multi-tenant architecture.

# 3. Technology Stack

## 3.1 Backend Framework

Laravel digunakan sebagai framework utama.

Fungsi:

* Routing.
* Authentication.
* Validation.
* ORM.
* Queue.
* Scheduler.
* File storage.
* Caching.
* Logging.
* Security middleware.

Versi yang digunakan mengikuti versi stabil yang kompatibel dengan lingkungan hosting dan dependensi proyek.

---

## 3.2 Admin Panel

Filament digunakan untuk membangun dashboard administrator.

Filament digunakan untuk:

* Dashboard.
* Form CRUD.
* Data table.
* Filter.
* Media management.
* Website settings.
* Audit log.
* Page Builder interface.
* Action confirmation.

Tampilan Filament dikustomisasi agar mengikuti Theme Village Nature tanpa mengubah perilaku inti dashboard.

---

## 3.3 Frontend

Frontend publik menggunakan:

* Laravel Blade.
* Tailwind CSS.
* Alpine.js apabila diperlukan.
* JavaScript ringan untuk interaksi tertentu.
* Leaflet untuk peta.
* Lucide untuk ikon frontend.
* Heroicons sebagai ikon bawaan atau fallback Filament.

Frontend tidak menggunakan framework SPA terpisah pada versi pertama.

---

## 3.4 Database

PostgreSQL digunakan sebagai basis data utama.

Alasan:

* Mendukung relasi data.
* Mendukung transaksi.
* Mendukung `JSONB`.
* Mendukung indeks yang fleksibel.
* Cocok untuk Page Builder berbasis JSON.
* Mendukung pengembangan pencarian lanjutan.

---

## 3.5 Penyimpanan Media

Media menggunakan Laravel Filesystem.

Tahap awal:

* Private local storage untuk file sumber.
* Public storage untuk derivative yang telah diproses.

Tahap lanjutan dapat menggunakan:

* S3-compatible object storage.
* Cloud object storage.
* CDN.

# 4. Architectural Principles

## 4.1 Separation of Concerns

Setiap bagian aplikasi memiliki tanggung jawab yang jelas.

Contoh:

* Controller menerima request.
* Form Request melakukan validasi.
* Service menjalankan logika bisnis.
* Model berinteraksi dengan basis data.
* Job menjalankan proses berat.
* Policy mengatur otorisasi.
* View menampilkan antarmuka.

---

## 4.2 Thin Controller

Controller tidak menyimpan logika bisnis yang kompleks.

Controller hanya bertugas:

1. Menerima request.
2. Memanggil service atau action.
3. Mengembalikan response.

---

## 4.3 Service-Oriented Business Logic

Logika penting diletakkan pada service atau action.

Contoh:

* `PagePublishingService`
* `MediaProcessingService`
* `WatermarkService`
* `MenuService`
* `SearchService`
* `AuditLogService`

---

## 4.4 Reusable Components

Komponen Page Builder, frontend, dan dashboard harus dapat digunakan ulang.

Komponen tidak boleh bergantung pada data Desa Kertajaya secara langsung.

---

## 4.5 Configuration over Hardcoding

Identitas desa dan theme tidak ditulis langsung di dalam view atau component.

Data diperoleh melalui:

* Website settings.
* Theme configuration.
* Environment variable.
* Database.

---

## 4.6 Secure by Default

Fitur keamanan aktif secara bawaan dan tidak bergantung pada konfigurasi operator non-teknis.

---

* Authentication.

# 10. Page Builder Rendering Architecture

Page Builder menggunakan renderer berdasarkan `component_type`.

Alur:

```text
Page
↓
Load Sections
↓
Sort by Position
↓
Load Components
↓
Resolve Component Renderer
↓
Render Blade Component
```

Contoh pemetaan:

```text
heading       → page-builder.heading
rich_text     → page-builder.rich-text
image         → page-builder.image
gallery       → page-builder.gallery
statistics    → page-builder.statistics
video         → page-builder.video
map           → page-builder.map
documents     → page-builder.documents
cta_button    → page-builder.cta-button
card_grid     → page-builder.card-grid
contact_block → page-builder.contact-block
```

Jika jenis komponen tidak dikenali, sistem:

1. Tidak menampilkan komponen.
2. Mencatat error.
3. Tidak menyebabkan halaman gagal seluruhnya.

```text

↓

↓

↓

↓

↓

↓
```

# 25. Architecture Constraints

1. Sistem harus dapat berjalan pada infrastruktur ekonomis.
2. Tidak boleh bergantung pada service berbayar untuk fungsi inti.
3. Seluruh fitur publik harus tetap berjalan ketika email gagal.
4. Media gagal proses tidak boleh dipublikasikan.
5. Sistem hanya melayani satu desa per instalasi.
6. Sistem hanya memiliki satu admin.
7. Theme tidak boleh memengaruhi business logic.
8. Konten harus dapat kosong tanpa menyebabkan error.
9. Struktur database harus reusable untuk desa lain.
10. Fitur kompleks di luar MVP dimasukkan ke backlog.

# 27. Kesimpulan

Village Website CMS menggunakan arsitektur modular monolith yang membagi sistem menjadi modul terpisah dalam satu aplikasi Laravel.

Arsitektur ini memberikan:
