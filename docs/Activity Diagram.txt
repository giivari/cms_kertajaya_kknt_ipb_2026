# 1. Pendahuluan

## 1.1 Tujuan Dokumen

Dokumen Activity Diagram menjelaskan alur aktivitas utama yang terjadi dalam Village Website CMS.

Dokumen ini digunakan sebagai dasar untuk:

1. Memahami urutan proses pada sistem.
2. Mengidentifikasi keputusan dan kondisi alternatif.
3. Menentukan interaksi antara Guest, Admin, dan Sistem.
4. Menjadi dasar perancangan antarmuka.
5. Menjadi dasar implementasi controller, service, dan validation.
6. Menjadi dasar penyusunan test case.
7. Melengkapi dokumen Use Case Specification.

---

## 1.2 Ruang Lingkup

Activity Diagram mencakup proses berikut:

1. Login administrator.
2. Logout administrator.
3. Mengubah password.
4. Membuat dan memublikasikan halaman.
5. Mengelola section dan komponen halaman.
6. Mengarsipkan halaman.
7. Mengelola berita.
8. Mengelola galeri.
9. Mengelola dokumen.
10. Mengelola Media Library.
11. Mengelola menu.
12. Mengelola lokasi peta.
13. Mengirim pesan narahubung.
14. Mengelola pesan narahubung.
15. Menggunakan pencarian.
16. Pencatatan audit log.

# 2. Notasi Activity Diagram

Notasi yang digunakan:

| Simbol        | Keterangan                                 |
| ------------- | ------------------------------------------ |
| Initial Node  | Menandai awal proses                       |
| Activity      | Menunjukkan aktivitas                      |
| Decision Node | Menunjukkan percabangan keputusan          |
| Merge Node    | Menggabungkan kembali alur alternatif      |
| Fork          | Memulai beberapa aktivitas paralel         |
| Join          | Menggabungkan aktivitas paralel            |
| Final Node    | Menandai akhir proses                      |
| Swimlane      | Memisahkan tanggung jawab aktor dan sistem |

Swimlane utama terdiri atas:

* Guest.
* Admin.
* Sistem.
* Email Service, jika diperlukan.

# 3. Activity Diagram Login Administrator

## 3.1 Tujuan

Menggambarkan proses autentikasi administrator menggunakan username, password, CAPTCHA, dan TOTP.

## 3.2 Alur Aktivitas

```text
Mulai
  ↓
Admin membuka URL khusus dashboard
  ↓
Sistem menampilkan formulir login
  ↓
Admin memasukkan username dan password
  ↓
Admin menyelesaikan CAPTCHA
  ↓
Sistem memvalidasi input
  ↓
Apakah format input valid?
  ├── Tidak
  │     ↓
  │   Sistem menampilkan pesan kesalahan
  │     ↓
  │   Sistem mencatat login gagal
  │     ↓
  │   Kembali ke formulir login
  │
  └── Ya
        ↓
      Sistem memverifikasi username dan password
        ↓
      Apakah kredensial valid?
        ├── Tidak
        │     ↓
        │   Sistem menambah jumlah percobaan gagal
        │     ↓
        │   Sistem mencatat login gagal
        │     ↓
        │   Apakah batas percobaan tercapai?
        │     ├── Ya
        │     │     ↓
        │     │   Sistem memblokir sementara proses login
        │     │     ↓
        │     │   Sistem menampilkan pemberitahuan
        │     │
        │     └── Tidak
        │           ↓
        │         Kembali ke formulir login
        │
        └── Ya
              ↓
            Sistem meminta kode TOTP
              ↓
            Admin memasukkan kode TOTP
              ↓
            Sistem memverifikasi kode TOTP
              ↓
            Apakah kode valid?
              ├── Tidak
              │     ↓
              │   Sistem mencatat kegagalan TOTP
              │     ↓
              │   Kembali ke input TOTP
              │
              └── Ya
                    ↓
                  Sistem membuat session baru
                    ↓
                  Sistem memperbarui waktu dan IP login
                    ↓
                  Sistem mencatat login berhasil
                    ↓
                  Sistem menampilkan dashboard
                    ↓
                  Selesai
```

## 3.3 Kondisi Khusus

1. Jika session admin masih aktif, sistem dapat langsung mengarahkan ke dashboard.
2. Jika CAPTCHA gagal, proses validasi kredensial tidak dijalankan.
3. Jika batas login gagal tercapai, sistem menerapkan rate limiting.
4. Session ID harus diperbarui setelah login berhasil.
5. Semua percobaan login dicatat dalam audit log.

# 25. Kesimpulan

Activity Diagram Village Website CMS menggambarkan alur proses utama antara Guest, Admin, Sistem, dan layanan pendukung.

Diagram aktivitas menunjukkan bahwa:

1. Website publik dapat digunakan tanpa login.
2. Akses administrator dilindungi oleh autentikasi berlapis.
3. Halaman dapat dibuat secara fleksibel melalui Page Builder.
4. Publikasi konten dilakukan setelah proses validasi dan preview.
5. Media digunakan secara terpusat melalui Media Library.
6. Pesan narahubung disimpan dan diteruskan sebagai notifikasi email.
7. Aktivitas penting administrator dicatat secara otomatis.
8. Konten arsip dan soft delete tidak dapat diakses oleh Guest.
9. Sistem tetap dapat berjalan meskipun belum memiliki konten.
10. Seluruh alur dapat diterjemahkan ke dalam antarmuka, service, controller, dan test case.

Tambahan:
Alur upload media wajib melewati watermark tak terlihat.
Media tidak langsung tersedia setelah upload.
Media harus berstatus verified sebelum dapat dipublikasikan.
